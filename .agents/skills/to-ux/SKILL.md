# Interface Design (to-ux)

Design an interface, generate something you can look at, and leave a record
of what was decided and what was rejected — so the next person does not
redesign it from scratch.

## First: what can you actually draw with?

**Check your own tool inventory before designing anything**, and say what
you found. Capability classes worth looking for, with current examples —
treat these as illustrations, not a definitive list, because the list goes
stale faster than this document does:

| Capability | Examples seen in the wild |
|---|---|
| Design-file access | Figma MCP (Dev Mode) |
| Generative UI mockups | Google Stitch, image generation |
| Inline rendering | a `visualize`-style MCP with a mockup or interactive module - renders SVG/HTML you can iterate on in the conversation |
| Look at what exists | a browser MCP, for screenshotting the running UI |
| Styling and system | theme, brand-guideline or design-system skills already installed |

**Delegate rather than improvise.** If a design tool is available, use it
and say which: *"Rendering this with the mockup module"*, *"Delegating
screen generation to Stitch"*. Where more than one fits, offer the choice
rather than picking silently.

**If nothing is available, say so before starting**, not after:

> "No design tooling is available here, so I can describe the interface but
> not show it to you. Figma or Stitch MCP, or an inline rendering tool,
> would make this much more useful."

An agent that quietly produces a wall of prose where a picture was wanted
has failed at this even if the prose is good.

## Read the design system first

If the repo root has a **`DESIGN.md`**, read it before designing anything.
It is an emerging Google Labs convention for describing a design system to
agents — machine-readable tokens in YAML front matter, rationale in the
markdown body — so an agent stops inferring intent from screenshots.
Schema, token types and gotchas:
[references/design-md.md](references/design-md.md).

Draw values from it rather than inventing them. When you write code,
reference its tokens instead of hardcoding hexes and pixel sizes. When a
design introduces a new token, add it in the same pass.

If the project has a design system but no `DESIGN.md`, offer to write one.
It is alpha and it will move, but it is the difference between a system an
agent can follow and one it has to guess at.

Do not confuse it with an index of design records: `DESIGN.md` at the repo
root is the token file; records live under `docs/design/`.

## Accessibility is part of the design

Not a review step afterwards. While designing, get these right rather than
discovering them later: colour contrast against the text it carries, touch
targets big enough to hit, a sensible focus and reading order, state that
is conveyed by more than colour alone, labels for anything an assistive
technology must announce, and behaviour when text is scaled up.

Designing this in costs nothing. Retrofitting it costs a rework.

Auditing **already-built code** against a standard is different work with
different inputs — that is not this skill.

## Recording it

Two artifacts: a written record, and something to look at.

**`docs/design/` is a companion tree to `docs/knowledge/`** — a deliberate
sibling, not a fallback. Design records and their samples live there,
git-native, and do not sync to the tracker KB. The sync carries `.md` only
and has no attachment path, so a synced record would publish its prose and
leave every image behind as a dead link.

    docs/design/<feature>/<Component>.md      the record
    docs/design/<feature>/resources/          the samples
    docs/design/components/                   cross-feature components

Link samples with **relative paths** — `![Empty state](resources/empty.png)`.
Absolute filesystem paths break for everyone who is not you.

Design *direction* with no images — principles, accessibility standards,
system-level guidance — belongs in the KB's **Design & Accessibility**
section instead, where it syncs and sits beside the rest of the knowledge.
Cross-reference the two rather than duplicating.

The record should carry the options considered, what was chosen, and what
was rejected and why — a screenshot with no reasoning tells the next person
nothing about whether they may change it.

## Iterate to code

A design is not finished when there is a picture of it. Carry it through:

1. **Show something.** Render or generate a first pass and get a reaction.
2. **Iterate on the artifact**, not on prose about the artifact. Change it,
   show it again. Two or three rounds beats one long description.
3. **Write the code** when the shape is agreed — from the design system's
   tokens, not hardcoded values, and with the accessibility properties in
   place from the start rather than added later. On Compose that means
   semantics and content descriptions written as you go; the equivalent
   exists on every platform.
4. **Look at the result** if a browser or screenshot tool is available. The
   built thing and the mockup diverge, and the built thing is the one users
   get.

Where the implementation is substantial, the work still belongs on tracker
stories — build it there rather than in one long unreviewable pass.

## What happens next

Judge the scale, because it decides where the work goes.

**A new screen, flow or capability** warrants requirements: move to
`to-prd`. The PRD carries the requirements; verification lives on tracker
stories.

**A tweak, a new state, a small reusable component** does not. Either
extend the existing PRD, or go straight to tracker stories via `to-issues`.

Acceptance criteria live on the stories in the tracker — never in a
document, and never in a local `docs/ac/` tree.
