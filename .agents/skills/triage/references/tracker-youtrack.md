# Tracker Binding: YouTrack (triage)

Connection facts from `.agents/config/story-tools.json`; credentials from
the story-tools installer - never collected in chat.

| Triage operation | YouTrack command |
|---|---|
| Query buckets | `search_issues` - e.g. `project: {KEY} has: -{tag}` for untriaged, `tag: needs-triage`, `tag: needs-info` |
| Read an issue fully | `get_issue` (+ comments) |
| Apply category roles | Prefer the project's `Type` field when it has one: `update_issue` → Type = Bug / Feature (boards color and swimlane by Type). Fallback where there is no Type field: `manage_issue_tags` → `bug` / `enhancement` |
| Apply state roles | `manage_issue_tags` - the role names ARE the tag names (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`) |
| Mark triaged | `manage_issue_tags` - on disposition (not `needs-info`): remove `needs-triage`, add `triaged`. Find untriaged work with `tag: -triaged #Unresolved` |
| List dimension values | `story_project_dimensions` - **fields only** (Subsystem/Type/Priority/Fix versions/Stage). It does NOT return tags. Pass `projectKey` explicitly: omitted, it derives the project from your focused story, which may be in another project. |
| List existing tags | `.agents/config/dimensions.md` (generated by yt-pull) - it lists **every usable tag**, workflow and topical, in separate sections. This is the only source that has them; the dimensions tool does not. Stale or absent? `story-reconcile/scripts/yt-pull.sh --dimensions-only`. Never mint a tag because you could not find a list - say you could not read it and ask. |
| Group work by topic | The project's own groupings live in the **Topical Tags** field, values listed in `.agents/config/dimensions.md`. Reuse one before adding. To add: append a line to `.agents/config/topical-tags.md` (the agents' list - it is committed and reviewed), then `story-reconcile/scripts/yt-pull.sh --dimensions-only --push-tags` carries it into the tracker. Nothing constrains what a tag looks like; name it so it groups the work usefully. Server tags are for cross-cutting state and one-off delivery batches; a grouping that will still mean something in six months belongs here. |
| Set Subsystem | `update_issue` → Subsystem (component ownership; list values first, confirm before setting) |
| Set release | `update_issue` → Fix versions (query later with `Fix versions: 1.2`); the field and its version values are project settings - if absent, note it for the maintainer, don't approximate with a tag |
| Link related issues | `link_issues` - always the most specific type: `duplicates` (then close the duplicate), `depends on` (ordering), `subtask of` (parent epic/feature), `discovered from` (provenance), `relates to` only when nothing sharper fits |
| Post triage notes / briefs | `add_issue_comment` |
| Put AC into the description | `story_add_ac` per item, or careful `get_issue` → edit → `update_issue` (canonical `## Acceptance Criteria` section) |
| Close (wontfix) | `update_issue` - set the resolution: State → Won't fix (and Stage → done column where the project has both fields) |

The installer pre-creates the full workflow tag set shared with All Users
(where the token allows); anything still missing is created on first use -
share those with the team in YouTrack so everyone sees the same triage
state. Adding a `Type` field to a project is
a one-time admin step (Project Settings > Fields > add the default Type
field); until it exists, the tag fallback keeps working. If the team later
prefers a custom "Triage" field over the state tags, only this table
changes.
